# ScamShield AI — Sample Inputs and Verified Outputs

Every block below was generated by running the **actual pipeline** over the curated demo
messages (`backend/api/samples.py`). Nothing here is hand-written.

Regenerate with:

```powershell
python scripts/seed_demo_data.py --clear   # runs the same pipeline and stores the results
```

The "Expected" column is the risk level documented in `samples.py`; the "Actual" column is
what the running system produced. A test
(`test_phase5_integration.py::test_every_sample_matches_its_expected_risk`) fails if these
two ever diverge.

> Explanation source `fallback` means Gemini was not configured in this environment. With a
> valid `GEMINI_API_KEY` the source becomes `gemini` and the narrative changes — the
> **detection does not**.

## Notes on the two control cases

**Genuine chat — LOW, 0/100.** Nothing fires. This is the baseline behaviour that
demonstrates the system is not simply flagging everything.

**Genuine bank alert — MEDIUM, 20/100.** This is a *known false positive* and it is
deliberately left visible:

* The ML model returns P(spam) ≈ 0.82 because the 2005-era UCI corpus barely contains
  transactional alerts — a textbook distribution-shift failure despite 98.55% test accuracy.
* Two mitigations were added: a weight-0 structural rule (`R_TRANSACTIONAL_ALERT_STRUCTURE`)
  and an ML damping factor of 0.25 that applies **only when no high/critical rule fires**.
  A scammer copying the format still trips the link, KYC, OTP, threat and payment rules.
* Effect: CRITICAL 100 → MEDIUM 20. We stopped there and documented it rather than tuning
  thresholds until the example read LOW.

This case is asserted in `test_phase2_rules.py::test_genuine_debit_alert_not_escalated` and
discussed in `docs/LIMITATIONS.md`.
